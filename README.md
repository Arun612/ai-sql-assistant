# AI SQL Assistant

An internal analytics assistant that converts natural language questions into SQL, executes them safely against a SQLite database, and returns plain-English explanations of the results.

Built with **FastAPI** + **Groq (llama-3.1-8b-instant)** + **SQLite**.

---

## Features

- **NL → SQL** via Groq LLM with schema-aware prompting
- **SQL Safety Validation** — SELECT-only enforcement, keyword blocklist, multi-statement detection
- **Plain-English Explanations** — results summarised for non-technical users
- **Chart Recommendations** — suggests bar/line/pie/table based on result shape
- **Query History** — full audit log in `query_logs.json`
- **`/explain-sql` endpoint** — explains any SQL query in plain English
- **Auto-seeded database** — 40 customers, 20 products, 200 orders ready on first run
- **Docker support**



## API Reference

### `POST /query`

Convert a natural language question to SQL and get results.

**Request:**
```json
{
  "question": "Show top 5 customers by number of orders",
  "include_chart_suggestion": true
}
```

**Response:**
```json

    "chart_type": "bar",
    "reason": "Bar chart best compares order counts across named customers.",
```

### `POST /explain-sql`

Explain what a SQL query does in plain English.

**Request:**
```json
{
  "sql": "SELECT c.name, SUM(p.price * o.quantity) AS revenue FROM orders o JOIN customers c ON o.customer_id = c.id JOIN products p ON o.product_id = p.id GROUP BY c.id ORDER BY revenue DESC LIMIT 10"

```

**Response:**

## SQL Safety Rules

The following operations are **always rejected**, regardless of how they appear in a query:

`DELETE` `UPDATE` `INSERT` `DROP` `ALTER` `TRUNCATE` `ATTACH` `DETACH` `CREATE` `REPLACE` `PRAGMA` `VACUUM`

Additional checks:
- Query must start with `SELECT`
- Multi-statement queries (`;` followed by another statement) are blocked
- SQL comments (`--`) are blocked
- Maximum query length: 2000 characters

## Architecture

```
POST /query
    │
    ├─ [1] Input validation (Pydantic)
    ├─ [2] NL → SQL  (Groq LLM, schema injected in system prompt)
    ├─ [3] SQL safety check (blocklist + SELECT enforcement)
    ├─ [4] Execute against SQLite
    ├─ [5] Results → plain-English explanation (Groq LLM)
    ├─ [6] Chart type recommendation (Groq LLM, optional)
    ├─ [7] Audit log entry written to query_logs.json
    └─ [8] JSON response returned
```

**Two-stage LLM design:** SQL generation and result explanation use separate API calls with tightly scoped system prompts. This keeps each call focused and improves output quality from the smaller model.

**Schema always in context:** The full schema (table names, column names, types, relationships, today's date) is injected into every SQL generation prompt — preventing the model from hallucinating column names.

---

## Limitations & Assumptions

- The Groq free tier has rate limits (~30 req/min). For high-traffic use, upgrade or add retry logic.
- `llama-3.1-8b-instant` handles straightforward queries well. For very complex multi-table analytics, switch to `llama-3.3-70b-versatile` via the `GROQ_MODEL` env var.
- The database is local SQLite — for production, swap `database.py` to use PostgreSQL via `psycopg2`.
- Query logs are stored in a flat JSON file — for production, use a proper database table.
- Date handling assumes queries run against the seeded dataset. "Last month" is computed relative to `date('now')` in SQLite.
